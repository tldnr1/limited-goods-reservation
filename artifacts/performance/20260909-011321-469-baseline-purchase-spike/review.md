# 첫 기본 실험: 워밍업 실패로 중단

- 실행: 2026-09-09 KST, baseline (Redis gate OFF).
- 예정 본 측정: 구매 시도 10 RPS × 60초. 성공한 구매마다 결제 접수를 추가하므로 전체 HTTP RPS와 다르다.
- 준비: perf DB 및 해당 Redis 키 초기화, 앱 재시작, health 및 Prometheus 3개 수집 대상 준비 확인.
- 워밍업: 별도 판매에서 구매 시도 10 RPS × 30초, VU 상한 20.
- 결과: 워밍업 기준 위반으로 자동화 종료(exit 1). 본 측정과 두 번째 실험은 실행하지 않았다. 중단 이유는 실행 오류이며 토큰 비용이 아니다.

## 판단 및 다음 단계

오류 발생 사실과 사후 재고 상태는 서로 대조할 수 있지만, 안정적인 성능이나 반복 측정의 일관성을 판단할 결과는 아니다. 워밍업 지연 수치를 정상 상태의 성능으로 사용하지 않는다. 본 측정용 원시 요청 기록과 Prometheus 시계열 수집 단계에는 도달하지 않았다. 서비스 로그에는 이전 실행 기록도 섞여 있으므로 이번 실행 시각(UTC 2026-09-08 16:16:54 전후부터 16:17:25까지)을 기준으로 읽어야 한다.

DB 연결이 길게 점유된 근본 원인은 아직 확정하지 않았다. 초기 JVM 기동 영향, 트랜잭션/락 대기, CPU 제약 등을 구분할 관측이 필요하다. 풀이나 VU 상한을 늘리는 것만으로 해결됐다고 볼 수 없다. 다음 작업은 해당 시점의 연결 점유 원인을 좁히고 워밍업 조건을 검토하는 것이다. 사용자 요청에 따라 추가 실험이나 애플리케이션 수정은 하지 않았다.

워밍업 추가 코드와 가이드 변경은 작업 트리에 남겼다. 실패 기록과 perf DB를 보존했으며 컨테이너는 실행 중이다.

## 추가 원인 검토 (2026-09-09, 재실행·설정 변경 없음)

남아 있던 Prometheus의 과거 데이터를 읽어 `diagnostic-warmup-metrics.json`과 `diagnostic-http-counts.json`으로 보존했다. 이전 자동 실행이 본 측정용 시계열 파일을 만들지 못한 것과, Prometheus 자체에 워밍업 기록이 남아 있는 것은 별개다.

### 확인된 사실

- AdmissionGate는 OFF다. `enter()`는 즉시 null을 반환하고 Redis permit을 차감하지 않는다. 결제 접수는 원래 gate 경로도 거치지 않는다.
- API마다 HikariCP 풀 하나가 있고 최대 연결은 각각 8개다. Worker는 4개, Mock PG는 2개로 별도다. API 2개의 16개 연결은 서로 빌려 쓸 수 있는 공용 풀이 아니다.
- 오류 당시 API1 로그는 `total=8, active=8, idle=0, waiting=8~9`였다. active는 대여된 연결 수이며, 모두 SQL을 실제 실행 중이라는 뜻은 아니다. 락 대기 중에도 연결을 보유할 수 있다.
- Hikari timeout 누적값은 API1=3, API2=0, Worker=0으로 로그와 일치한다. API1의 관측된 최대 연결 대여 시간은 2.889초, API2는 0.997초였다.
- UTC 16:17:35 조회 시점의 마지막 샘플에서 API1/2는 active=0, idle=8로 회복했다. 지속적으로 연결이 반환되지 않는 누수를 뒷받침하지 않는다. 단일 실행으로 모든 누수 가능성을 배제한 것은 아니다.

| 워밍업 HTTP 누적 결과 | API1 | API2 |
|---|---:|---:|
| 구매 201 | 275 | 25 |
| 결제 접수 202 | 22 | 275 |
| 결제 접수 500 | 3 | 0 |

구매·결제 합산 요청 수는 각각 300건이지만, 처리 종류는 크게 치우쳤다. Nginx는 현재 기본 round-robin이고 k6는 구매 응답 뒤 결제를 순서대로 호출한다. 이런 반복 순서와 분배 방식의 조합이 편향을 만들었을 가능성이 있다. 위 표는 전체 워밍업 누적값이며, 오류 순간의 정확한 요청 배치를 증명하지는 않는다.

### VU 20과 연결 16을 바로 비교할 수 없는 이유

VU는 k6의 시나리오 실행 슬롯이다. 이 시나리오에서는 구매→결제 접수를 순차 수행하며 DB 연결이나 API 인스턴스에 고정 배정되지 않는다. 따라서 '16개 처리 + API당 2개 대기'가 보장되지 않는다. 실제 로그부터 API1에서만 8~9개 연결 획득 대기가 보였다. API2의 정확한 같은 순간 대여 수는 알 수 없다.

Prometheus scrape는 5초 간격이다. 보존 시 조회 간격을 1초로 지정했지만 원본의 시간 해상도가 높아지는 것은 아니다. active/pending 샘플은 짧은 고갈 구간을 놓쳤고, 누적 timeout 및 최대 대여 시간 지표와 오류 로그가 이를 보완한다. 정확한 순간 동시 요청 수는 복원할 수 없다.

### 원인 후보와 수정 전 확인 순서

코드상 구매는 동일 상품 행의 비관적 락을 트랜잭션 종료까지 보유하며, 락 이후 인당 합산·주문/항목/점유 저장·응답 DTO 조회도 수행한다. Worker의 결제 확정도 같은 상품 행을 잠근다. 그러므로 '느린 초기 트랜잭션 → 동일 재고 행 대기 중 연결 점유 → API1 풀 대기 증가 → 같은 풀을 쓰는 결제 접수 타임아웃'은 가능한 설명이다. 실제 락 대기 기록이 없어 확정된 근본 원인은 아니다.

`PaymentService.start()`는 PG를 호출하지 않는다. Worker의 PG HTTP 호출도 트랜잭션 메서드 사이에서 실행되므로, 코드상 API가 외부 PG 응답을 기다리며 연결을 잡는 구조는 발견되지 않았다. 초기 JVM/JPA 처리 비용, CPU 제한의 영향은 여전히 후보지만 CPU throttling/JFR/SQL별 소요 기록이 없어 분리할 수 없다.

다음 수정 판단 전에는 (1) 초기 요청의 트랜잭션/SQL/락 대기 시간, (2) API별 요청 종류와 처리 시간, (3) CPU throttling 및 JVM 초기 비용을 좁혀 관측해야 한다. 그 후 트랜잭션 단축, 점진적 워밍업, 요청 분배, 풀/접수 제한 조정 중 필요한 것을 선택한다. 현재 자료만으로 풀 8개가 본질적으로 부족하다거나 증설이 해결책이라고 결론내리지 않는다.
